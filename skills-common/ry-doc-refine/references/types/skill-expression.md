# Skill 文档表达

仅在目标是 `SKILL.md`、Skill references 或完整 Skill 文档包时读取。Skill 文档既是表达，也是运行接口；本文件帮助重新组织叙事，同时识别哪些变化会改变实际能力契约。

## 保护运行接口

当前措辞、章节和说明顺序不是保留对象，可以围绕更好的能力心智整体重写。以下内容则可能直接改变 Skill 怎样被发现和执行：

- `name` 与 `description` 表达的能力和触发范围；
- 输入、输出、完成条件和用户授权；
- 权限、工具、高代价操作和外部影响；
- `SKILL.md` 与 references 之间的加载关系；
- scripts、assets、平台字段和其他运行依赖；
- 唯一维护源、动态事实入口和资源拓扑。

可以主动发现并讨论这些接口的问题。改变它们所表达的选择时，区分当前契约、建议中的新契约和用户已经确认的目标；确认后整体实施，不把新旧行为混在同一运行包中。用户当前请求已经明确给出新目标或授权对应变化时，不重复确认。

## 区分触发前后

frontmatter `description` 是触发前可见的能力与场景契约，不是 `SKILL.md` 的压缩摘要。优先表达 Skill 能做什么、哪些请求或场景需要它，再按实际区分价值保留关键排除条件。执行流程、内部 resources 和触发后的工作方法不应淹没发现信息。

`SKILL.md` 只有在 Skill 已经触发后才会加载。正文中的“遇到某场景时使用本 Skill”不能帮助首次触发；它只有在限定触发后的职责、处理后续请求或帮助维护时才有价值。正文根据当前任务选择分支、加载 reference，属于触发后的内部路由。

改写 `description` 时不拘泥原句，但要检查目标宿主仅凭名称和新 `description` 是否仍会在预期场景调用，并避开相邻能力。需要改变触发范围时，把它作为契约候选处理，而不是伪装成文案优化。

## 重建能力叙事

目标 AI 触发 Skill 后，应能尽快建立正确能力心智：这项能力解决什么问题，当前请求从哪里进入，需要依据什么判断，去哪里取得必要信息，以及什么状态算完成。

旧稿的流程和目录不自动成为主模型。可以使用任务路由、对象关系、决策模型、状态变化或输入到结果的路径重新统摄正文，也可以删除无决策价值的通用常识、重复规则、创作过程和未来假设。理由只保留到足以帮助泛化或阻止误解。

叙事重建可以直接调整文档内部标题、段落、表格、示例和顺序。跨文件移动内容、增加或删除 reference、改变加载时机时，需要额外判断目标 AI 的可见上下文是否变化；如果变化会影响行为，它属于契约重组而不只是排版。

表达文件结构时区分当前实例和扩展模式。当前 Skill 包的目录树列出真实资产；说明未来怎样增加同类资源时，可以使用 `<document-type>-expression.md` 等角色明确的参数。不要用占位符掩盖当前文件，也不要用当前清单冒充完整扩展边界。

## 保持决策与产物一致

普通表达优化可以直接完成；涉及能力契约的新选择时，可以继续分析并提出完整方案，不因缺少其他 Skill 而停止思考。实施边界是用户是否已经确认该选择，而不是改动看起来有多大。

完成后检查：

- `description`、正文、references 和实际资源是否描述同一项能力；
- 已确认目标是否完整取代旧叙事，没有历史补丁或冲突规则残留；
- 新建议是否被误写成已经确认的运行事实；
- 目标 AI 能否依据实际加载内容处理未枚举的新情况；
- 文件拆分和资源入口是否与真实可见性一致。

如果根因属于能力设计，审阅任务应清楚报告；修改任务可以在当前对话中提出方案，并在取得相应确认后继续实施，不要求用户另行安装或调用其他 Skill。
