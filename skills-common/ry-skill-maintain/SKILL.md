# Skill 维护

同一 Skill 可以被多个 Agent 或客户端安装和使用。维护时若直接改动当前副本，原本应共同演进的正文会逐渐分叉；但并非每个 Skill 都有中心来源，也并非每个修改都应共享。

本 Skill 在准备修改某个 Skill 本身时，读取其维护声明，判断本次修改应维护中心、当前副本，还是只保留反馈。它维护的是 Skill 的来源关系，不约束 Skill 的正常使用、任务输出或项目文件。

## 工作区接入

在希望采用这套维护关系的工作区中加入：

> 当准备修改某个 Skill 自身时，加载 `ry-skill-maintain`；读取该 Skill 的 `SKILL.md` frontmatter，并按 `metadata.ry_agent_update` 所表达的维护关系处理。字段不存在时，按当前仓库或客户端的默认规则维护。

该提醒负责让 Agent 在修改前进入本 Skill；metadata 决定进入后应遵循的关系。没有声明字段的 Skill 不因本 Skill 可用而自动纳入中心维护。

## 读取维护关系

读取即将修改的 `SKILL.md` frontmatter 中的 `metadata.ry_agent_update`：

| 值 | 维护关系 | 本次修改的落点 |
|---|---|---|
| `source` | 当前副本始终跟随中心正文 | 修改中心，再刷新当前副本 |
| `local` | 当前副本是本地版本 | 只修改当前副本 |
| `disabled` | 当前正文不交给 Agent 修改 | 保持不变，只反馈问题或建议 |
| 字段缺失 | 未声明本生态的维护关系 | 回到当前仓库或客户端的默认规则 |

字段值无法识别时不猜测。说明当前值及其维护关系无法确定，等待用户决定。

`metadata` 表达的是 Skill 已有的维护关系，不是脱离任务场景机械执行的状态机。当前客户端的原生能力和用户对本次修改的授权仍然有效，但不能改变 `source`、`local` 与 `disabled` 分别表达的中心、本地和不修改关系。

## `source`：维护中心正文

`source` 表示当前副本与中心正文保持一致。对 Skill 本身的修改先进入中心，再由当前客户端按需取得新版本；不要直接把修改留在安装副本中。

### 进入中心

- 远程中心：`https://github.com/miracloon/my-skill-repo.git`
- 本地中心工作副本：`~/workspace/ai-meta/my-skill-repo/`
- 中心目标：本地中心工作副本与目标 Skill 的 `metadata.ry_source_path` 组合后的目录
- 客户端副本：当前 Agent 实际加载和使用的 Skill 目录

本地中心工作副本存在时，直接在其中取得远程当前变化；不存在时，clone 远程中心到该位置后继续。中心目标不存在、clone、同步、提交或推送遇到实际阻塞时，报告原因和已完成状态；不要以修改安装副本代替中心更新。

本地中心工作副本是读取、修改、验证和提交中心事实的操作界面。修改前同步远程、修改后提交并推送，仍是在维护同一个中心，而不是建立第二个维护源。

### 修改并发布

- 检查中心目标已有修改、远程变化与当前副本反馈之间的关系；涉及当前 Skill 的差异或冲突先向用户说明并完成协调。
- 说明要解决的问题、中心目标路径、拟议修改及影响，并取得本次源更新授权；当前请求已经明确授权时，不重复索要同一授权。
- 以中心目标的当前内容为基线应用有效修改。当前副本只用于提供问题证据或临时验证，不用于整体覆盖中心目录。
- 同步更新中心目标的 `metadata.version`。版本保持带引号的三段字符串；兼容性修补通常递增末位，更大的行为变化按实际影响调整。
- 执行目标 Skill 适用的格式、链接和行为验证。错误显式暴露，不用忽略失败换取发布完成。
- 提交只包含当前 Skill 和本次修改确实需要的关联文件，不夹带中心工作副本中的其他工作。
- 推送到远程中心。只有远程中心已经包含新正文，才算完成共享源更新；仅修改本地中心工作副本不算完成。

### 刷新当前副本

中心推送完成后，使用当前客户端原生的 Skill 管理方式刷新当前副本，不用文件复制另建一套同步流程。更新后核对当前副本的名称、版本和必要内容已对应中心正文。

中心已推送与当前副本已刷新是两个状态：客户端未安装、命令不可用或刷新失败时，明确报告当前副本尚未更新，不宣称其他客户端已经自动同步。

需要 Hermes 操作时，读取 [Hermes 客户端路由](references/clients/hermes.md)。其他客户端使用各自的原生能力；命令未知时先核实，不以手工复制伪装为原生更新成功。

### 私有需求：转为 `local`

`source` 不保留只属于当前环境的 Skill 正文变化。用户明确要求当前副本承载私有需求时，这不是 `source` 的例外，而是当前副本转为 `local`：

- 在当前客户端副本中将 `metadata.ry_agent_update` 改为 `local`；
- 再按下文的 `local` 语义完成私有修改；
- 不修改或推送中心，也不再对此副本使用会覆盖本地内容的原生更新命令；
- 明确告知用户：当前副本已退出中心更新链，成为本地版本。

## `local`：维护当前副本

- 修改直接发生在当前客户端的 Skill 目录。
- 不修改本地中心工作副本或远程中心，不把这次变化作为中心更新处理，也不改写中心的 `metadata.version`。
- 本地变化存在后，不再对该 Skill 使用会以中心版本覆盖本地内容的客户端原生更新命令；以后需要引入中心变化时，先审查并合并差异。
- 完成后说明修改内容、适用原因，并明确该副本是客户端本地版本。
- 用户明确要求回收本地修改时，把本地内容作为反馈，对照中心当前正文选择具有共享价值的部分，再按 `source` 流程更新、提交和推送中心；不要整体覆盖中心，也不要在中心更新后自动更新当前本地副本。

## `disabled`：保持不变

- 不修改当前客户端副本、本地中心工作副本或远程中心。
- 向用户报告发现的问题，可以提供建议，但不把建议落实为 Skill 修改。
- 只有用户明确改变这一维护决定后，才按新的语义继续。
