# Orchestrate 路由

## 目标

把一个开发范围编译成可以脱离当前对话独立执行的任务定义。不假设执行者是谁——同一份文档既可能由当前对话接着执行，也可能交给独立上下文或子代理。

编译对象来自已经收敛的 Design、Plan 的一个分段，或本次讨论中已经达成一致的范围。讨论已收敛但尚未落成 Design 时，在本路由内完成一次轻量提炼即可，不强制先创建 Design 文档。

## 执行方的处境

编译的全部取舍都来自执行方的真实条件：它有完整的编码能力，能读到项目和代码，但看不到讨论，并且会忠实执行文档写下的每一句。

由此有三条同时成立的事实：

- 写下的每一句都会被执行，多写一句就是多一分膨胀；
- 没写的就不会发生，讨论中已经成立而文档未载的内容等于不存在；
- 含糊之处会被执行方自行决定、当作已决定，并且不会回报。

它是有能力但没有方向的执行者。方向、边界和验收由你提供，实现由它负责。

## 意图与指令的分工

任务定义不可能覆盖全部情况，也不应试图覆盖。执行方一定会遇到文档没有写到的岔路，此时它的判断依据只有两个来源：你给出的意图，或它自己的默认习惯——后者就是漂移。

因此详尽度应当两端重、中间轻。这两者是替代关系而不是并列原则：**中间之所以能轻，正是因为头尾够重**。头尾不重时，中间必须靠穷举指令兜底，而穷举必然有漏，漏掉的地方仍由默认习惯补全。

**头**是用户视角的意图——最终要达成的操作、心智或组织结构，不是技术目标。写"改一处就能让三个 profile 同时生效，不必记住哪些文件要同步改"，而不是"实现配置合并模块"。它给执行方一个在实现有多种选择时可以自行校准的参照。

**尾**是验收，同时承担两个职责：说明做到哪算完成，以及说明做到哪就该停。写成可观察的状态、可运行的命令或可检查的产物，不写"功能正常工作"。

## 约束的表达

否定式边界的信息密度最高。肯定式指导可以从目标推断，否定式边界推不出来，而且往往正是执行方默认会做的事。讨论中被否决过的方向尤其要显式带上——它们在讨论里有完整理由，在执行上下文中完全不可见。

软约束和硬约束都有价值，区别在于是否承载优先级信息：

- 有效的软约束能回答"什么情况下可以不做"，给出倾向和放弃条件，让执行方在冲突时有据可依；
- 无效的软措辞只承载犹豫或周全感，不提供任何优先级信息。对忠实执行的接收方，它不会产生"柔和"效果，只会变成噪声或被放大成任务。

硬约束同样需要带上它为什么硬。没有理由的硬约束在遇到冲突时只留下两条路——违背，或扭曲实现去满足；带上理由，执行方才能判断当前情况是否仍在其覆盖范围内。

无法判断或不打算规定的地方显式授权："这里的实现方式你自己判断。"显式授权与留空不写不等价，后者会被自行填补并当作已决定。

## 应当省略的内容

删掉后执行结果不变的内容就该删掉。常见的有：

- 复述 AI 默认行为，例如先阅读项目文档、了解目录结构；
- 无信息的质量口号；
- 泛化的"注意错误处理""做好边界检查"——它们不改变行为，却诱发过度防御；
- 创作过程、讨论来源和已被放弃的推导；
- 文件级实施步骤清单。

最后一条要特别注意：步骤清单是规格膨胀伪装得最好的形态。它看起来像写清楚了，实际是把实现猜想固化成施工要求，并且可能在第一步完成时就已过时。

## 结构

最小必要内容：

- **用户意图**：最终要达成的操作、心智或组织结构；
- **目标与范围**：本次要改变什么；
- **边界**：不做什么，含讨论中明确否决的方向；
- **输入与当前基线**：相关文件、现状事实和交接基线；交接基线是包含本任务定义、执行方实际接手的 commit。任务文件不需要自引用该 commit 的 hash，交接时提供精确 hash，或用“首次提交本任务定义的 commit”标识。
- **验收**：可观察、可运行或可检查的完成判断；
- **完成后**：更新或创建 State，形成完成提交并回报 commit、实际做法、偏离及未完成项。

推进思路可选，只在存在真实依赖顺序时给出。写方向不写教程：交代每步完成后达到什么状态，以及为什么是这个顺序，让执行方能据此自行调整。

不设"实施要点"一类默认栏目——列成常规结构会诱使为填满它而生成内容。

参考 [../assets/task.example.md](../assets/task.example.md)。实用的长度标准是执行方一次读完就能开始动手；需要往回翻就太长了。

## 配套动作

任务定义形成后提交一次，包含任务定义的这个 commit 就是交接基线，也是回滚点和 Reconcile 的 diff 起点。提交前检查工作树；存在归属不明、不能安全纳入基线的未提交改动时停止并请求用户处理，不擅自提交、隐藏或回滚。
在任务定义中点明：执行方完成后需要更新或创建 State，形成可验收的完成提交，并回报该 commit、实际做法、偏离及未完成项。执行过程可以按项目规则产生中间提交；上游最终以交接基线到完成提交的 Git 区间验收。独立上下文不加载本 Skill，这是提交与 State 要求到达执行方的通道之一；另一条是项目自身的 `docs/development/DEV_WORKFLOW.md`。

## 停止

本路由的结果是任务定义和交接基线。完成后呈现它们并停止，不自动开始执行，也不替用户选择执行位置——在当前对话执行、新开上下文换模型还是使用子代理，是用户的调度决策。
用户要求在当前对话继续执行时，转入 [develop.md](develop.md)。外派执行完成并返回原编排上下文时，转入 [reconcile.md](reconcile.md) 验收，不重新进入 Orchestrate。
