# Reconcile 路由

## 目标

让 Design、Plan、任务定义、State、实际实现和相关项目文档重新描述同一件事，并把完成后的活动材料退出默认运行路径。Reconcile 不是生成更多总结，也不把阶段材料直接同步到项目长期治理。

## 确定授权

用户只要求审阅、检查或评估时保持只读，发现问题后报告。用户要求完成、修复或收束当前开发时，可以在原范围内修复明确问题、重新验证并更新阶段材料；新的重大取舍仍需用户裁决。

是否调用宿主原生代码 review、独立 agent 或项目现有检查机制，根据环境和风险决定。实现质量审阅不能替代下面的阶段一致性检查。

## 审阅外派结果

执行发生在独立上下文或子代理中时，当前对话往往仍持有完整的讨论背景。这带来一个特有风险：**用讨论记忆替代码补全意图**，把"想到过但任务定义没写、代码也没做"的内容判为已完成。

因此判断依据限定为：任务定义、基线以来的 Git 区间、执行方的完成说明和实际代码。讨论中有而任务定义与代码都没有的内容，报告为**任务定义缺陷**——既不默认算数，也不默默补上。这条反馈会直接改善后续编译质量。

同时做两类检查：

- **完成度**：实际交付是否满足任务定义的目标、边界和验收；执行方声明的做法与代码是否一致；偏离是否有说明。
- **质量**：既查缺，也查多。超出范围的改动、未要求的兼容层或备份路径、防御性分支、重复事实源、顺手完成的重构和自动生成的说明，都属于应当报告的溢出。

结论的去向由用户裁决——当前对话小修、编译返工任务定义、或回到讨论重新裁决——不自动修复。

## 一致性检查

读取当前 Design、存在的 Plan、State、相关代码与验证结果，并按需读取可能受影响的项目长期治理文档。检查：

- 实现是否满足 Design 的目标、边界和成功判断；
- Plan 的当前路径是否仍成立，指定型约束是否被遵守；
- State 是否准确区分已验证、进行中、未实现、未验证和阻塞；
- 文本是否把计划、候选、实验或局部实现写成已经成立的完整事实；
- 代码中是否存在阶段材料没有解释的重要偏移、旧实现或试验残留；
- 已失效的计划、状态和开放问题是否仍在默认读取路径；
- 本次变化是否产生值得进入项目长期治理的候选。

发现矛盾时按信息身份处理：Design 决定意图，代码和运行证据决定实现事实，State 描述当前差距，项目长期文档决定持续治理身份。不要静默选择写得更完整的一方。

## 长期治理候选

只有同时满足以下条件的内容才进入候选：

- 已由用户确认，或属于 Design 授权范围内已经形成的稳定决定；
- 已在项目中实际落地；
- 有代码、测试、运行结果或其他可靠证据支持；
- 会持续影响未来 AI 对项目的理解、开发或维护。

候选按需说明：变化内容、证据、可能影响的长期文档，以及仍未闭合或明确不应集成的内容。临时探索、执行历史、被放弃路径和未验证判断不进入长期治理。

`ry-docs-control` 或项目等价治理机制把候选当作输入而不是事实结论，仍需核验当前代码和长期文档。除非用户明确要求同时更新长期治理，否则形成候选后停止。

## 收束与归档

完成后更新 State，使未完成、未验证和长期治理状态准确可见。任务已经闭合时不得让 State 继续表现为活跃工作。

阶段整体闭合时，归档是一个带核对的动作而不只是一条原则：

1. 核对实际交付与活动材料，清除 `pending`、`draft` 等伪活动状态；
2. 将仍成立的事实晋升到长期文档（或形成候选交由长期治理机制处理）；
3. 确认测试、生成、链接和引用检查通过；
4. 将整个目录从 `active/<identifier>/` 移到 `history/<identifier>/`。

项目已有归档约定时服从项目约定。阶段尚未整体闭合时只更新 State，不提前归档。不为形式完整生成独立的 Summary 或 Review 文件。
