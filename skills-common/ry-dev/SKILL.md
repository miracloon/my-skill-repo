# 阶段性开发治理

## 定位

本 Skill 用于在中大型开发中跨上下文保持用户意图、执行方向、当前状态和项目现实的一致性，同时保留 AI 在已确认边界内自主规划、探索和实现的空间。

核心心智：**存在任务定义时，开发执行受任务定义控制，不受生成它的对话上下文控制**。本 Skill 参与准备与收束，产出可以脱离对话独立存在的任务定义；执行发生在当前对话、另一个上下文还是子代理中，由用户决定，不替用户选择。没有任务定义的小范围 Develop 可以直接以当前明确请求为边界。

它不替代 coding agent 或具体 harness 的规划、编码、并行、上下文管理和代码审阅能力。优先使用现场环境的原生能力，不要求存在特定命令、平台或外部开发 Skill。

## 信息身份

- **Design**：用户意图、边界、已确认决定和开放问题的语义来源；不证明已经实现。
- **Plan**：Design 承载不下时形成的可选执行投影；可以随证据调整，不表示实际进度。
- **任务定义**：Design 或 Plan 面向执行者的一次编译投影；用完即止，不参与事实权仲裁。
- **State**：当前已验证、进行中、未验证、阻塞和下一步的工作事实；不是计划或流水账。
- **代码、测试和运行结果**：实现事实；不自动代表用户接受该行为。
- **项目长期治理文档**：项目当前长期有效的定位、结构、约束和运转现实；阶段产物不能直接覆盖。

尚未决定的内容保持开放身份。不要为了形成完整方案，把用户倾向、AI 候选、探索方向或未验证实现升级为已经确认、完成或有效的事实。

## 规格尺度校准

文档的详尽度、边界的严格度和验收的严苛度，应匹配任务的真实量级和用户的真实心智，而不是匹配"一份合格开发文档该长什么样"。

典型失败是把小需求理解成系统：产出完整的分层、规范和验收，执行方忠实实现，最终交付物与真实需求不在同一量级。反向信号——**文档体量接近或超过预期改动本身的体量时，大概率已经膨胀**。

这条作用于全部路由：Design 不把小需求写成大系统，Plan 不为小任务建阶段，Orchestrate 不为小范围写长规范，Reconcile 不用系统级标准审一个小工具。

## 路由

根据用户当前要获得的结果选择路由，并完整读取对应文件：

| 当前目标 | 加载 |
|---|---|
| 探索意图、形成或更新 Design | [references/design.md](references/design.md) |
| 判断是否需要 Plan，或形成、调整跨阶段 Plan | [references/plan.md](references/plan.md) |
| 把一个开发范围编译成可独立执行的任务定义 | [references/orchestrate.md](references/orchestrate.md) |
| 在当前对话实施、实验、验证或继续一个开发范围 | [references/develop.md](references/develop.md) |
| 审查一致性、收束状态、归档或识别长期治理候选 | [references/reconcile.md](references/reconcile.md) |
| 用户明确要求完整闭环、连续执行或使用 Goal 类模式跑完 | [references/full-loop.md](references/full-loop.md) |

Orchestrate 与 Develop 不是互斥选项，而是可选的前后关系：Develop 既可以承接 Orchestrate 的产物，也可以在范围已经清楚时直接进入。区分触发语义——用户要**现在做**时进入 Develop，要**准备好让人做**时进入 Orchestrate。外派执行完成后，原编排上下文进入 Reconcile 回收和验收结果，不重新进入 Orchestrate。

用户语义优先于文件状态。一个请求组合多个阶段时，先加载主要路由；只有确实进入另一阶段时才加载下一份 reference，不为理解全貌预读所有文件。

若用户只触发本 Skill 而没有说明当前目标，轻量检查相关阶段材料和项目状态，说明当前所处位置并建议下一路由；不要自动启动设计、编排、开发或完整闭环。若任务明显是单上下文可完成的小修改，不创建阶段材料。

## 运行强度与停止

默认使用**阶段模式**：只完成用户当前要求的路由、指定范围或一个 Plan 顶层分段，然后呈现结果。可以建议下一步，但不自动跨阶段。

只有用户明确要求完整完成、连续执行、全自动闭环或 Goal 类运行时，才进入 Full loop。完整闭环不扩大原任务的修改、外部行动或长期治理授权，也不自动编译并派发任务——执行位置的选择属于用户的调度决策。

无论采用哪种模式，出现以下情况都应停止并请求用户裁决：

- 新发现会改变 Design 的目标、边界或用户可见结果；
- 需要用户做价值、体验或其他关键取舍；
- 指定型 Plan 步骤无法按要求继续；
- 将引入新的重要外部契约、重大风险或不可逆影响；
- 证据不足以支持下一项关键决定。

在 Design 已确认的范围内，AI 可以自主选择实现、调整目标型或探索型 Plan、修复范围内问题并完成相称验证。变化应回到对应信息层，不把所有现场调整都升级为用户决策。

## 文档载体

默认载体是 `docs/development/`，项目已有约定时服从项目约定：

```text
docs/development/
├── DEV_WORKFLOW.md      # 项目自身的开发文档治理约定
├── active/
│   └── <identifier>/    # 正在推进的阶段材料
└── history/
    └── <identifier>/    # 已结束的阶段记录
```

标识符只要求稳定可辨，不绑定版本号语义。默认同一时间只有一个活动标识符，项目确有并行需要时可以覆盖。目录内按任务需要包含 Design、Plan、任务定义、State 或其他说明，没有强制文件组合；一次性小任务不创建目录。`history/` 不是当前实现事实源，只在追溯决策、回归来源或迁移背景时读取。

`DEV_WORKFLOW.md` 是 `ry-dev` 在项目侧的配套组件，只有采用这套开发治理的项目才引入。仓库级基础模板由用户手动复制为项目自己的 `docs/development/DEV_WORKFLOW.md`；从建立起，项目副本就是本项目的当前正文，可以随实践独立演化，不与基础模板持续同步。本 Skill 不负责创建、检查、初始化或更新它，但会在存在时遵守其中的项目约定。

只读取当前任务相关的项目治理入口、Design、存在的 Plan、存在的 State 和当前路由 reference；历史材料只在追溯确有必要时加载。

模板只提供内容身份和最小结构，不要求填满：

- Design：[assets/design.example.md](assets/design.example.md)
- Plan：[assets/plan.example.md](assets/plan.example.md)
- 任务定义：[assets/task.example.md](assets/task.example.md)
- State：[assets/state.example.md](assets/state.example.md)

同一语义只保留一个当前来源。更新现有文档时重写当前状态，不在末尾累积版本补丁；物理文件是否拆分服从任务规模，但各类信息身份不能混淆。

## State 归属

State 属于当前持有推进权的上下文：在当前对话执行时由 Develop 维护，在独立上下文或子代理中执行时由执行方维护，外派结果回收后由 Reconcile 维护。时间上不重叠，不存在双写。

State 由第一个执行者创建，Orchestrate 阶段不创建——此时还没有工作事实，生成的只会是一份全部未开始的清单。例外是多轮外派：需要掌握哪些范围已派、已回、已验收时，State 提前建立并退化为委托台账。

## 长期治理边界

Reconcile 负责识别并核验可能值得进入项目长期治理的变化。只有已确认、已落地、已有证据且会持续影响未来判断的内容才成为候选；临时探索、执行历史和未闭合问题不进入长期治理。

是否以及怎样更新长期治理文档，由项目的 `ry-docs-control` 或等价治理机制独立判断。除非用户明确要求同时完成长期治理更新，否则只形成候选，不自动调用下一套治理流程；这不妨碍 Reconcile 继续完成状态收束和归档。阶段归档前应把长期治理状态收束为 `integrated`、`deferred` 或 `none`；`deferred` 只表示明确留待以后治理审阅，不承诺自动处理。
